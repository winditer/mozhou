# FeelFish 竞品分析

> 调研日期：2026-10-22 ｜ 信息源以官网/官方文档/官方 Release Notes/App Store 为主，第三方评测仅作交叉验证并标注可信度
> 结论标注方式：`[S1]` 等编号对应文末「信息来源」。凡未取得证据的一律写「未查证」。

---

## 0. 关键结论（TL;DR）

1. **它不是"AI 续写器"，而是"把长篇小说当成一个工程项目来管理的 Agent 工作台"。** 核心资产不是模型，而是 `.feelfish` 项目目录里的规则/角色/设定/章节/智能上下文/智能体/技能，以及一套"AI 只能通过工具改文件、改完要你审批"的机制 [S2][S4][S8]。
2. **产品自我定位明确拒绝"全自动批量产文"**，官方原话是"绝不是靠全自动化的方式去生产'数字泔水'，服务对象始终是专业创作者" [S7]。这决定了它的 Agent 自主度上限：**多步执行 + 关键节点人工确认（计划→大纲→正文）**，而非无人值守跑完整本。
3. **形态是"桌面为主 + 移动为辅（遥控器）"**：Windows / macOS / HarmonyOS PC 三端全功能客户端，iOS / Android / HarmonyOS 手机端只做「看稿、记灵感、远控桌面 AI」，且仅对高级/专业会员开放 [S1][S3]。
4. **定价是"订阅 + 积分双轨"**，人民币 ¥0 / 29 / 59 / 199 四档（年付 6 折），积分即 token 消耗计量 [S5]。免费档 500 万积分 ≈ 约 5000 字产出，**试用窗口极小**，这是它转化漏斗上最明显的裂缝。
5. **2026 年 4.0/4.1 的演进方向值得警惕**：从"写作工具"扩到"多部门 AI 工作室（秘书部/编辑部/质检部）+ 项目时光机 + 视频/漫剧/有声书" [S6][S7]——它在往"内容生产 OS"上长，而不只是"写作软件"。

## 1. 一句话定位

**FeelFish = 面向专业小说/网文/剧本作者的桌面级「AI Novel Writing Agent」工作台**：以本地小说项目为容器，用规则 + 角色 + 设定 + 智能上下文构建可被 Agent 检索的长篇记忆，用「方案 / 智能体 / 技能」编排多 AI 分工，让 AI 在项目内**直接新建与改写章节文件**，所有改动以 Diff 形式待人确认。

一句话对比：字面意义上更像「小说版的 Cursor / Claude Code」——文件系统 + Agent + Skills + 审批门，而不是「网页版 AI 续写」。

## 4. 工作流拆解（用户实际怎么用）

```
① 建项目（选模板：小说 / 剧本 / 自由创作 / 拆书）
        ↓
② 用 Agent 对话搭框架：风格规则 → 主角/配角卡 → 世界观设定 → 分卷大纲
        ↓
③ 生成「智能上下文」：AI 读已写正文 → 产出 风格 / 角色近况 / 剧情记录 / 伏笔清单 / 角色关系图
   （= 把"越来越长的设定文件"压成"信息密度更高的摘要"，解决窗口爆炸）
        ↓
④ 配「方案」：选内置方案（专业辅助 / 多智能体 / 智能规划 / 游戏冒险）或自建
   —— 勾选启用哪些智能体、谁当主智能体、给每个智能体挂哪些技能、绑哪个模型
        ↓
⑤ 写章节（两条路径）
   A. 智能规划模式（重流程）：下任务 → AI 出「创作计划」→ 你确认 → 出「章节大纲」→ 你确认
      → 按大纲写正文 → 自动回写 角色文档 / 设定文档 / 剧情记录 / 后续创作计划
   B. 专业辅助模式（轻流程）：直接对话写，或 Cmd+K 就地生成/改写单段
        ↓
⑥ 审稿：Diff / 待确认变更 → 接受或退回；段落标注 + 引用原文喂给 AI 精准改
        ↓
⑦ 一致性维护：智能上下文按需增量更新（默认 78% 阈值触发压缩，可调 50–70%）
        ↓
⑧ 多部门并行：编辑部写正文 ‖ 质检部审前章 ‖ 秘书部管配置/导出/找回历史
        ↓
⑨ 沉淀：把有效做法写成技能（SKILL.md）→ 复用 / 分享到市场
        ↓
⑩ 交付：云盘自动同步 + 项目时光机保底 → 导出 / 朗读 / 转漫剧视频（4.1）
```

**Agent 自主度的真实边界（重要）**：

| 环节 | 自主度 | 证据 |
|---|---|---|
| 读哪些文件 | **高**：Agent 主动调工具读文件，不必你贴 | 「AI 有强大的工具调用能力，如果 AI 需要读取文件内容，是可以主动调用工具读取」[S2] |
| 多步任务推进 | **高**：以任务列表方式推进整章创作 | 「要求 AI 必须以任务列表的方式来推进每一章的创作」[S4b] |
| 计划/大纲 | **低**：必须你确认才继续 | 「只有在你确认后，AI 才会开始执行」[S12] |
| 改文件 | **中**：改前给 Diff，改后可回滚 | 4.0 待确认变更 + 单文件历史 [S6] |
| 文档回写 | **高**：写完自动更新角色/设定/剧情记录 | [S12] |
| 跨部门派单 | **中高**：AI 判断归属并转接，但有确认提示 | 「自动帮你转接」+ 确认提示 [S6] |
| 一次跑完一本 | **明确不做** | 拒绝"数字泔水"、拒绝全自动 [S7] |

> 结论：这是「**Human-in-the-loop 的自动化**」——每个"高自主"环节都嵌了一个审批门，用自主度换可控性。这既是它的克制，也是它相对"一键生成整本"类工具的核心差异点。

### 7.3 积分 ↔ token ↔ 字数换算（官方口径）[S5b]

以 DeepSeek V3.2 为例：

- 输入：**28,000,000 积分 / 百万 token**；输出：**42,000,000 积分 / 百万 token**（≈ 发 2 字 28 积分，回 2 字 42 积分）
- 首条 100 字发送 ≈ 2000 积分；AI 返回 100 字 ≈ 3000 积分；续聊 100 字（带 200 字历史，含缓存）≈ 2400 积分
- 长对话逼近上限时，单次请求 ≈ 28 万积分（年付价 ≈ 3.5 分钱）
- **1 亿积分 ≈ 10 万字**（改得少）／**2–3 万字**（反复改）
- GPT-5.1 消耗约为 DeepSeek-3.2 的 **近 5 倍**；GLM-5 同样 1 亿积分只能出约 2 万字 [S1]

## 9. 优点（具体，≥5）

1. **上下文工程是真做了，不是 prompt 堆料。** 规则/角色/设定/章节/智能上下文五层分离，每层可勾选是否随对话携带，并能实时看到"这次带了哪些文件、吃掉多少 token" [S2]。绝大多数竞品只给一个"世界观输入框"，差了一个数量级的可控性。
2. **智能上下文解决的是真痛点：设定文件越长越难用。** AI 从已有正文自动抽取风格/角色近况/剧情记录/伏笔清单/角色关系图，把"越来越长的原始素材"换成"信息密度更高的摘要"，并且**不可手改**（保证一致性），支持多份 + 自定义抽取提示词 [S2b]。这是对抗"长篇越写越崩"的核心机制。
3. **Agent 编排能力接近开发者工具，而非写作玩具。** 方案（Solution）/智能体（Agent）/技能（Skill）三层，`.feelfish/agents/<id>.md` 带 YAML frontmatter（`tools: all|readonly`、`skills: []`），技能走 `SKILL.md` + `references/` 的**渐进式披露三级加载**，MCP 可扩展 [S4][S8]。这套设计明显对齐了 Claude Skills / MCP 生态，可迁移性强。
4. **自动化闭环设计得很克制也很对。** 智能规划模式：计划→确认→大纲→确认→正文→**自动回写角色/设定/剧情记录/后续计划**，等于每次创作都在"顺手更新知识库"，把维护成本降到接近 0 [S12]。
5. **改稿安全性做到长篇可用级别。** Diff 预览 + 待确认变更 + 单文件历史 + 整项目时光机 + 云盘 30 天版本，四层保底 [S6][S7]。AI 改稿最怕丢稿，这一层是长期使用的信任基础。
6. **桌面端生产力细节密度高**：对话窗外拖双屏、段落标注+引用原文、折叠已完成步骤、角色对聊、朗读/语音输入、多主题、快捷键自定义 [S6][S6b]。这些是"每天用 4 小时"的人和"每周试一次"的人的分水岭。
7. **BYOK 免费 + 模型中立 = 获客与信任双赢。** 4.0 起自配模型可免费用软件；不同部门/智能体可绑不同模型（贵的写正文、便宜的做摘要）[S4c][S6]。对预算敏感的专业作者吸引力极强。
8. **明确的价值观叙事（反"数字泔水"）**，把"人机协同"和"全自动量产"划清界线 [S7]。这在小红书/知乎这类"AI 味"高度敏感的创作者社区是有效的信任资产。

## 10. 缺点与用户吐槽（具体，≥5）

1. **免费额度形同虚设，试用漏斗断裂。** 免费 500 万积分/月 ≈ **约 5000 字**产出（按 1 亿≈10 万字折算）[S5][S5b]。写完一章就没了，用户根本没机会体验"智能上下文对长篇的帮助"——而这恰恰是它最贵的卖点。**这是最容易攻击的软肋**。
2. **积分消耗不可预测、且是"隐性持续扣费"。** 官方自己写明：不只是生成才扣，来回对话、Agent 读文件、秘书部推荐、语义搜索、对话取名、智能上下文更新**全都扣积分**[S5b]。用户难以预估"写一章要花多少钱"，天然产生"被割"的感受。
3. **计费黑箱：完整价目表要登录才看。** 官网只给 DeepSeek V3.2 一个样例，其余模型「请登录后访问 /account/credits 查看」[S5b]。这直接导致了真实的负面口碑：黑猫投诉平台存在一条题为**《FeelFish宣传不符实，功能虚假还耗积分，退钱并公示》**的投诉（编号 17396221061，页面现已 404/需登录，具体内容**未能核实**）[S18]。可信度提示：仅标题可证，正文未验证。
4. **移动端是半成品，且语言标注为英语。** 手机端只做"看稿/记灵感/远控"，且仅高级/专业会员可用；iOS App 版本 1.1.1、评分 **1.0 / 5（仅 1 条评分）**、语言标注「英语」[S16][S3]。第三方文章也把"只有 PC 客户端、没有 APP 和完整网页版"列为用户最常抱怨的点 [S11]。
5. **语义检索有硬门槛：单文件 ≤100KB（约 3 万字）。** 超过就搜不到，且同步后需几十秒到几分钟才生效 [S3]。写超长章节的作者会直接踩坑。多设备并发编辑还会冲突，只能手工选"本地覆盖云"或"云覆盖本地"[S3]。
6. **上下文窗口依然是硬约束，需要用户自己"做减法"。** 官方文档整篇在教用户"别一次带太多文件""信息少一些可以减少注意力干扰""建议每个章节新开对话"[S2]。也就是说：**它把上下文工程的一部分认知负担转嫁给了用户**——不是"开箱即用"，而是"要学"。
7. **技能/智能体体系学习曲线陡。** 要写 YAML frontmatter、短横线命名、≤1024 字 description、要埋"用户真实会说的中文触发词"、还要调"触发不足/触发过度"[S8]。官方技能指南本身就有 6 章 + 3 附录——**这是给 power user 的，不是给作者的**。
8. **营销噪音大，第三方内容可信度低。** 检索中发现大量 CSDN / 博客园 / 今日头条的"测评"，实际是被标注"可能是商业推广软文"的 SEO 内容（博客园页面顶部直接有平台提示）[S19]，部分甚至包含**编造功能**（如"逻辑扫描自动标红矛盾""自动生成故事时间线""内置 GPT-4o/Gemini-1.5 等 9 个模型"），在官方文档中查无实据 [S15]。这会污染用户预期，反过来放大"宣传不符"的投诉。
9. **无团队协作、无 API/CLI。** 项目是单用户本地目录 + 云盘备份，没有多人实时协作、评论、审批流；也没有官方 API/CLI 让你把它的 Agent 接进自己的流水线 [S4][S3]。工作室场景只能"共用一个账号/传项目包"。
10. **迭代激进导致版本割裂。** 4.0（2026-07）→ 4.0.48（2026-09）→ 4.1.0 **beta 需手动安装、不自动更新**[S6b]，且 4.1 已加入视频/漫剧/有声书等**与写作强相关度存疑**的能力，有"功能蔓延、注意力分散"的风险。
11. **导出能力表述含糊。** 官方只提"导出文稿"，未见格式清单（txt/markdown/docx/epub 各自支持度）——**未查证**。对要投平台的作者，导出/排版是很硬的决策项。

## 11. 对我们的启示

### 11.1 产品层面

1. **护城河应该建在"项目资产"上，而不是模型上。** FeelFish 的锁定点是 `.feelfish` 目录（规则/角色/设定/技能/方案），不是 DeepSeek。**我们要设计一个"导出后仍然有价值"的项目结构**（如 Markdown + frontmatter 的开放工程目录），既降低迁移顾虑，又让"迁移成本"变成"内容资产"而非"格式人质"。
2. **"智能上下文"这个机制必须做，而且要做得更自动、更可观测。** 它把"设定文件越长越难用"这个反直觉的真问题解决了。我们可以做得更狠：**自动增量维护 + 变更历史 + 冲突高亮 + 每章写完后的一致性体检报告**（这是 FeelFish 明确缺的：它没有"矛盾检测"）。
3. **审批门是产品哲学，不是功能缺陷。** 它的形成是"高自主 + 关键节点确认"。我们可以更前进一步：**分级授权**（"这一章允许 AI 直改，下一章只允许提建议"），比统一的"每次都要点确认"更贴实际。
4. **Skills/MCP 生态要直接兼容，不要自造。** 它已经把 `SKILL.md` / `AGENTS.md` / MCP 当事实标准（连"技能名不能以 Claude/Anthropic 开头"这种约束都继承了）。**兼容 = 可反向收割它的社区资产**；自造格式 = 从零养生态。
5. **移动端不要做"全功能 App"，要做"三件事"**：看稿、记灵感、**审批 AI 变更**。FeelFish 的移动端恰恰漏了最关键的第三件——它只能"发指令"，不能"审 Diff"。这是明确的空位。
6. **"部门/秘书"这种隐喻包装值得抄。** 作者不理解"多 Agent 编排 / 子智能体调度"，但理解"编辑部、质检部、秘书"。命名即产品。

### 11.2 商业层面

7. **免费额度要按"任务"给，不要按"积分"给。** "5000 字/月"无法验证价值；"第一本书免费写到 5 万字"能让人真正跑到第 20 章、体验到一致性收益，再付费。**用体验深度换转化率**。
8. **定价页必须给"每万字多少钱"的计算器。** 它的价目表要登录才看，且只说"1 亿积分≈10 万字（改得少）"——"改得少"三个字就是黑箱。我们把"每章成本预估 + 请求级明细 + 月度预算上限"做在明面上，直接吃它的信任缺口。
9. **BYOK 免费是必选项，不是差异化。** 它已经这么做了，我们不能没有；差异化要落在"BYOK 用户也能享受我们的一致性/检索/编排能力"。
10. **价格不必正面拼。** 它把自建 DeepSeek 缓存通道的成本优势打到 ¥0.85–1.7/万字。我们更该做"分层"：轻度用户按 token、重度用户按"整本包干"（如 ¥99/本 不限改稿次数），把不确定性从用户身上挪走。

### 11.3 增长与口碑层面

11. **它的 SEO/软文投放极重（CSDN、博客园、今日头条、AI 导航站全覆盖），且已经开始反噬。** 我们如果做内容，宁可做"可验证的实测"（公开提示词、公开积分消耗截图、公开同一段落多工具对比），用一个"可信评测"占位，比投 50 篇软文更持久。
12. **盯住它的投诉关键词**：「积分消耗快」「宣传不符」「只有 PC 端」。这三个词就是它用户的流失原因，也就是我们的获客文案。
